# 標準開発ワークフロールール (Standard Development Workflow Rule)

機能実装、リファクタリング、バグ修正などの開発タスクを進める際は、以下の2段階ゲートウェイ（Quality Gates）を厳格に遵守すること。

---

## 🚪 Gate 1: 実装前プロセス（計画策定・PdM & テックリードレビュー）

実装コードを書く前に、必ず「正しい計画」を策定し、多角的なレビューと承認を経ること。

1. **実施計画の立案**:
   - 課題の根本原因、改修方針、対象ファイル、完了条件を明確にする。
   - **リファクタリングタスクの場合**: 必ず `.agents/rules/refactoring-guide.md` の4段階プロセス（安全網確認 ➔ テスト非接触での実装リファクタ ➔ デグレゼロ検証 ➔ テスト整理）を計画に組み込むこと。
2. **PdM & テックリード 合同レビューの実施**:
   - **シニアPdM視点**:
     - コアバリューやプロダクト思想と合致しているか？
     - ユーザー体験（UX）を損なう副作用や不自然な仕様変更はないか？
   - **テックリード視点**:
     - アーキテクチャの妥当性（ハイドレーション、並行性、浮動小数点の桁落ち、KISS/YAGNI原則など）。
     - 単なる表面的な修正になっていないか？（例: `prevLength` の不整合やゴースト自動保存の誘発など、波及する潜在リスクを網羅できているか）。
     - 最適なアルゴリズム・データ構造が選択されているか？
3. **計画のアップデート**:
   - レビューで指摘されたリスク・改善要件を取り込み、実施計画を強固にアップデートする。
   - 必要に応じて計画書に反映する。
4. **ユーザーの承認取得**:
   - アップデートした計画をユーザーに提示し、承認（Approval）を得てから実装に着手する。

---

## 🚪 Gate 2: 実装後プロセス（重複テスト検査 ＆ シニアQA・テックリードレビュー）

実装完了後、コミットする前に必ず「品質検証」「重複検査」「厳格なレビュー」を行うこと。

1. **自動検証の全件実行**:
   - 型チェック、Lint、単体テスト、E2Eテストを自動実行し、全件パスを確認する。
     ```bash
     npm run type-check && npm run lint && npm run test:unit && npx playwright test
     ```
2. **重複テスト検査 (Test Deduplication Audit)**:
   - 新規作成・修正したテストが、**既存の単体テストやE2Eテストと無駄に重複していないか** を機械的に検査する。
   - 単体テスト（ホワイトボックス：ロジック、境界値、型安全性）と E2Eテスト（ブラックボックス：画面遷移、ブラウザ結合）の責務分離（テストピラミッド）が保たれているか確認する。
3. **シニアQAエンジニア & テックリード 合同レビューの実施**:
   - **シニアQAエンジニア視点**:
     - テストカバレッジの網羅性（正常系・異常系・境界値・エッジケース）。
     - 偽陽性（テストが誤ってパスする）や偽陰性（Flakyテスト）のリスクがないか。
     - ユーザーの誤操作（ボタン連打・二重送信、オフライン時の切断等）に対する耐性があるか。
     - **リファクタリング監査**: プロダクションコードの不具合に合わせてテストコード側を都合よく書き換えていないか（セルフテストの罠の排除）。
   - **テックリード視点**:
     - コードアーキテクチャガイドライン（`.agents/rules/code-architecture-guide.md`）の遵守。
     - 安全なリファクタリング原則（`.agents/rules/refactoring-guide.md`）の遵守。
     - エラーの握りつぶしや過剰コードの排除（Fail-Fast原則）。
     - 計算量、メモリリーク、クリーンな依存関係。
4. **レビュー結果報告とコミット承認**:
   - レビュー評価（判定・評点）および重複検査結果をユーザーに報告し、承認を得てからコミットを実行する。
